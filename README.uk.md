# Transparent Gateway

[English](README.md) | Українська

Transparent Gateway спрямовує дозволений клієнтський трафік через HTTP, HTTPS,
SOCKS4 або SOCKS5 проксі, які надав адміністратор. Проєкт прозоро проксіює TCP,
підтримує два маршрути для DNS і зберігає адресу призначення, яку вибрав клієнт.

Проєкт призначений для мереж і проксі-сервісів, якими ви керуєте або на
використання яких маєте явний дозвіл. Він не збирає публічні проксі й не обходить
CAPTCHA, блокування або обмеження частоти запитів.

Для чистого встановлення почніть із [вимог](#вимоги), потім підготуйте
[мережеву схему](#мережева-схема-для-першого-запуску) і виконайте
[перший запуск](#перший-запуск). У наступних розділах пояснено архітектуру та
конфігурацію, яку створюють ці команди.

## Як це працює

```text
Дозволена клієнтська мережа (CLIENT_CIDR)
│
├─ TCP
│  └─ iptables REDIRECT :12345
│     └─ redsocks → egress relay :12000 → зовнішній проксі → адреса призначення
│
└─ UDP/53
   ├─ адреса входить до DNS_DEFAULT_RESOLVER_IPS
   │  └─ REDIRECT :5053 → DNS-over-HTTPS
   │     └─ позначений TCP → redsocks → зовнішній проксі → DNS_DOH_IP:443
   │
   └─ адреса будь-якого іншого DNS-сервера
      └─ TPROXY :5353 → DNS-релей UDP-to-TCP
         └─ позначений TCP → redsocks → зовнішній проксі → початковий DNS-сервер:53
```

Обидва DNS-маршрути використовують налаштований пул проксі. Вони відрізняються
лише способом доставки DNS-повідомлення до сервера:

- звичайні системні запити йдуть через DNS-over-HTTPS до налаштованого публічного
  DNS-сервера;
- запит до іншого DNS-сервера перетворюється з UDP DNS на DNS-over-TCP і
  доставляється за початковою адресою.

Gateway не бачить, чи програма виконала `dig name`, чи `dig @server name`. Маршрут
вибирається за IP-адресою призначення пакета.

## Компоненти

- **gateway** — єдиний привілейований контейнер. Він запускає `iptables`,
  `redsocks`, egress relay, DoH relay і DNS-релей UDP-to-TCP у мережевому просторі
  імен хоста.
- **fetcher** паралельно завантажує кандидатів з явно увімкнених і дозволених
  джерел: локального списку та HTTPS-джерела.
- **validator** виконує обмежені за часом асинхронні перевірки
  HTTP(S)/SOCKS4/SOCKS5 через кожен проксі, використовує налаштовані дані доступу,
  відсіює витоки клієнтської IP-адреси, знаходить ASN зовнішньої адреси в локальній
  базі та зберігає повну затримку й кількість послідовних успішних перевірок.
- **asn-updater** завантажує MMDB-базу origin ASN із ліцензією PDDL, перевіряє
  опубліковану контрольну суму SHA-256 та атомарно оновлює спільну локальну базу.
- **ranker** оцінює затримку й стабільність, за потреби штрафує повторення ASN і
  підмереж та публікує резервний і активний пули заданого розміру.
- **redis** зберігає останній перевірений пул із постійним журналом AOF.

### Конвеєр дозволених проксі

Конвеєр замінює ручне обслуговування активного пулу, але кожне джерело все одно
потрібно явно дозволити. Проєкт не збирає довільні списки публічних проксі. Кожне
джерело реалізує `ProxySourceConnector` із `validator/sources/base.py`. Реалізації
лежать у `validator/sources/` і реєструються вручну в
`validator/sources/__init__.py`. Самої появи Python-файлу в цьому каталозі
недостатньо, щоб виконати або ввімкнути його.

```text
налаштовані конектори
       │
       ▼
fetcher  ──→ proxy_pool:raw:v1
                    │
                    ▼
validator ─→ proxy_pool:validated:v1
                    │
                    ▼
ranker   ──→ proxy_pool:reserve:v1
                    │
                    ├──→ proxy_pool:active:v1
                    └──→ transparent-gateway:validated:v1 (сумісність із gateway)
```

Fetcher, ASN updater, validator і ranker працюють як окремі непривілейовані
сервіси Compose. Замість прямих викликів вони передають один одному повні JSON-
знімки через Redis. Кожна публікація спочатку записує дані в унікальний
тимчасовий ключ, а потім атомарно замінює попередній знімок. Читачі ніколи не
бачать частково записаний пул.

Конфігурація конекторів містить два явні списки: типи конекторів, дозволені для
цього розгортання, і активні екземпляри. Активний конектор також повинен бути
зареєстрований у коді та вказаний у `allowed_connector_types`.

Ranker поєднує виміряну затримку з обмеженим бонусом за послідовні успішні
перевірки. Повторення перевірених ASN штрафуються; те саме стосується повторень
мереж IPv4 `/24` та IPv6 `/48`. Менеджер пулу може читати резервний ключ, а
вбудований egress relay використовує сумісний активний ключ.

### Перевірка протоколу й анонімності

Validator не обмежується відкриттям TCP-порту кандидата. Він виконує справжнє
узгодження протоколу проксі й через отриманий маршрут звертається до echo-сервісу,
яким керує оператор:

- HTTP-запити через звичайний або загорнутий у TLS HTTP-проксі;
- SOCKS4/SOCKS4a `CONNECT`;
- SOCKS5 без авторизації або з логіном і паролем, `CONNECT` та перетворенням
  доменного імені на боці проксі;
- HTTP- або HTTPS-запит через установлений маршрут.

Спочатку validator звертається до того самого echo-сервісу напряму й дізнається
власну зовнішню адресу. Кандидат відхиляється, якщо сервіс знову бачить цю адресу
джерелом запиту або знаходить її в `Forwarded`, `X-Forwarded-For`, `X-Real-IP`,
`Client-IP` чи іншому відомому заголовку. Проксі, який приховує адресу, але додає
`Via` або іншу ознаку проксіювання, отримує клас `anonymous`. Без таких ознак —
`elite`. Сам заголовок `Via` повідомляє про використання проксі, але не розкриває
IP-адресу клієнта, тому не є причиною відхилення.

Echo-сервіс має повертати JSON із полем `backend_peer` (або `origin`) та об’єктом
`headers`. Для ізольованого лабораторного стенда цей контракт реалізує
`test-echo.py`. Контролюйте echo-сервіс самостійно: сторонній сервіс бачить зовнішню
адресу кожного кандидата і стає частиною довіреної зони перевірки.

ASN визначається за зовнішньою адресою, яку побачив echo-сервіс, а не за значенням від
конектора джерела. Наданий джерелом ASN зберігається лише як `source_asn` для
діагностики. Ranker читає перевірене значення `network.asn`; невідомі значення
штрафуються, а їхня частка в активному пулі обмежується. Якщо локальна MMDB-база
відсутня, пошкоджена або застаріла, validator залишає попередній повний знімок.

Якщо кандидат має `credential_ref`, validator і egress relay читають його з одного
доступного лише для читання сховища. HTTP(S) підтримує Basic proxy auth, SOCKS5 —
логін і пароль, а SOCKS4 використовує ім’я користувача як User ID. Секрети ніколи
не записуються до Redis або журналів.

### DNS-релеї

`gateway/doh_dns.py` приймає сире UDP DNS-повідомлення, вкладає його в HTTPS POST
із типом `application/dns-message` та перевіряє TLS-сертифікат за налаштованим SNI.
DoH-сервіс задається фіксованою IP-адресою, щоб запуск не залежав від DNS. Його
TCP-сокет отримує позначку `0x53`, тому HTTPS-з’єднання також проходить через
зовнішній проксі.

`gateway/udp2tcp_dns.py` приймає через TPROXY запити до інших DNS-серверів, читає
початкову адресу, додає двобайтову довжину DNS-over-TCP та виконує обмін через
позначений TCP-сокет. Відповідь повертається через UDP-сокет `IP_TRANSPARENT`,
прив’язаний до початкової IP-адреси DNS-сервера й порту 53. Тому клієнт бачить
відповідь саме від того сервера, до якого звертався.

Для порту 53 egress relay перевіряє DNS-over-TCP через одноразовий тунель. Невдалі
кандидати тимчасово відкладаються, а успішні отримують перевагу для наступних
DNS-запитів. Справжній клієнтський запит завжди отримує новий тунель.

## Вимоги

- Linux-хост із systemd, IPv4 TPROXY, policy routing, `iptables` і connection
  marks. Описаний перший запуск перевірено на Debian 13;
- Git і Python 3;
- Docker Engine із плагіном Docker Compose;
- права root на gateway;
- окрема клієнтська мережа, маршрут якої проходить через gateway;
- один або кілька дозволених HTTP/HTTPS/SOCKS проксі;
- DNS-сервери з підтримкою DNS over TCP для маршруту до явно вказаного сервера;
- окремий Linux-клієнт із Python 3 для повної перевірки маршруту.

Реалізація залежить від Linux та працює лише з IPv4. Константи
`IP_TRANSPARENT`, `IP_RECVORIGDSTADDR`, `IP_PKTINFO` і `SO_MARK` належать до
Linux socket API.

docker --version

systemctl --version
```

Проєкт не встановлює Docker і не налаштовує мережеві інтерфейси хоста.

```

## Мережева схема для першого запуску

Gateway потрібна адреса в клієнтській мережі. Клієнт має використовувати цю адресу
як єдиний шлюз IPv4 за замовчуванням. Окремий шлях для керування дуже бажаний:
помилка в маршрутах не повинна закрити доступ до обох машин.

У всій інструкції використовується одна схема:

```text
Клієнтська мережа:          192.168.91.0/24
Клієнтська адреса gateway:  192.168.91.1
Адреса тестового клієнта:   192.168.91.2
Шлюз клієнта за замовчуванням: 192.168.91.1
```

`CLIENT_CIDR` — це вся клієнтська мережа (`192.168.91.0/24`), а не окрема адреса
gateway. Адресу `192.168.91.1` потрібно призначити інтерфейсу gateway, а на клієнті
вказати її шлюзом за замовчуванням. Це налаштування хоста або гіпервізора;
`tgctl.py` навмисно їх не змінює.

## Перший запуск

Клонуйте репозиторій на Linux-хост, який маршрутизуватиме клієнтську мережу.
Інтерактивне налаштування запитає адресу цієї мережі та дані одного дозволеного
проксі. Пароль вводиться без відображення в терміналі та записується лише до файла,
який Git ігнорує.

```sh
git clone https://github.com/Va1b0rt/TransparentGateway.git
cd TransparentGateway
sudo python3 scripts/tgctl.py configure
```

Що потрібно вводити:

| Запит | Значення |
| --- | --- |
| Client IPv4 subnet | Мережа за gateway, а не мережа керування. Для схеми вище: `192.168.91.0/24`. |
| Proxy protocol | Протокол, який указав оператор проксі: `http`, `https`, `socks4` або `socks5`. Це не протокол сайта призначення. |
| Proxy host or IP | Адреса дозволеного зовнішнього проксі. Не вводьте адресу gateway або echo-сервісу. |
| Proxy port | Порт, отриманий разом з адресою проксі. |
| Username and password | Відповідайте `yes`, лише якщо проксі вимагає логін і пароль, після чого введіть надані оператором значення. |
| Validation echo URL | Натисніть Enter для публічного сервісу першої перевірки або введіть URL власного сумісного echo-сервісу. |

Адреса проксі та дані доступу не входять до репозиторію. Їх надає сервіс, яким ви
керуєте або на використання якого маєте дозвіл.

`configure` створює чотири робочі файли з обмеженими правами:

```text
.env
inventory/connectors.json
inventory/upstreams.jsonl
secrets/proxy-credentials.json
```

Git ігнорує ці файли. Команда відмовляється їх перезаписувати. Для зміни
працюючого встановлення редагуйте наявні файли, а не видаляйте їх і не вводьте все
заново.

Перед запуском привілейованого контейнера перевірте створену конфігурацію:

```sh
sudo python3 scripts/tgctl.py check
```

Команда перевіряє власників і права файлів, формат `host`/`port`, посилання на дані
доступу, клієнтську мережу, URL echo-сервісу та сформовану конфігурацію Compose.
Вона не змінює `iptables` або маршрути.

Запустіть шість сервісів і дочекайтеся появи проксі в активному пулі:

```sh
sudo python3 scripts/tgctl.py up --timeout 300
```

Перший `up` збирає образи, запускає контейнери, чекає на придатний проксі та
встановлює `/etc/systemd/system/transparent-gateway.service`. Під час наступних
завантажень служба використовує поточну робочу копію, тому не переносьте й не
видаляйте каталог репозиторію. Для сервісів Compose навмисно вказано
`restart: "no"`: їхнім життєвим циклом керує systemd.

Після першого успішного запуску використовуйте systemd:

```sh
sudo systemctl status transparent-gateway.service --no-pager
sudo systemctl restart transparent-gateway.service
sudo python3 scripts/tgctl.py down
sudo journalctl -u transparent-gateway.service --no-pager -n 100
```

`tgctl.py down` зупиняє службу systemd і чекає на зупинку її контейнерів. Якщо
перший `up` завершився помилкою до встановлення служби, команда напряму зупинить
частково запущений Compose-проєкт. Не використовуйте `docker compose down`: після
видалення контейнерів поза systemd служба типу oneshot усе одно може показувати
стан `active`.

Перегляньте стан сервісів і пулу без виведення адрес проксі та паролів:

```sh
sudo python3 scripts/tgctl.py status
```

`ACTIVE_POOL ready=1` доводить, що наданий проксі пройшов перевірку. Цей результат
ще не підтверджує проходження трафіку з іншої машини через gateway.

### Оновлення встановленого gateway

У каталозі встановленого проєкту вкажіть гілку, тег або коміт із `origin`:

```sh
sudo python3 scripts/tgctl.py update main --timeout 300
```

Команда перевірить, чи змінені файли коду, підготує нову версію в окремій
робочій копії Git, перевірить її з наявними налаштуваннями та збере образи.
Поточні контейнери в цей час працюватимуть. Після підготовки команда замінить
їх, зберігши проєкт Compose і томи даних. `.env`, список проксі та паролі не
перезаписуються. Якщо файли коду змінені, команда покаже їхні назви та зупиниться.

Для успіху потрібні шість працюючих сервісів без помилок перевірки стану,
свіжі пули з успішним циклом валідації після заміни та справжній запит через
relay до echo-сервісу з адресою активного проксі. `--timeout` задає час очікування
готовності; відкат отримує окрему спробу з тим самим лімітом. Завантаження й
збирання мають власні ліміти часу. Під час заміни можливий розрив з’єднань.
Це перевірка на gateway; клієнтський маршрут і DNS перевіряються окремо нижче.

Якщо заміна або перевірка не вдалася, команда поверне попередній код та образи
й перевірить їхню роботу. Навіть після успішного відкату команда завершиться з
помилкою: `ROLLBACK PASS` означає, що попередня версія працює, а не що оновлення
вдалося. Якщо відновлення теж не вдалося, команда повідомить про це окремо.
Після перерваного оновлення повторіть відновлення зі збереженого журналу:

```sh
sudo python3 scripts/tgctl.py update --recover --timeout 300
```

Після аварійного завершення процесу або вимкнення хоста відновлення запускається
цією командою. Git залишається на встановленому коміті (detached HEAD), локальні
гілки не пересуваються. Наступне оновлення отримає потрібну версію з `origin`.
На старому встановленні спочатку потрібно через Git отримати версію, яка містить
цю команду.

Не видаляйте приватний каталог `runtime/update/`, який Git ігнорує.
`images.json` фіксує образи для `tgctl.py` і наступного запуску через systemd,
а `transaction.json` потрібен для відновлення. Керуйте сервісами через `tgctl.py`
або systemd: прямі команди Compose не враховують ці зафіксовані образи.
Під час оновлення чи відновлення не видаляйте збережені теги образів.

Цей варіант працює з наявними шістьма сервісами та встановленою службою systemd.
Зміни конфігурації Redis або підключення томів команда відхиляє. Відкат не
повертає попередній вміст даних у томах: зміна їхнього формату потребує окремої
процедури перенесення.

Перевірку готовності на gateway можна запустити окремо:

```sh
sudo python3 scripts/tgctl.py ready --timeout 300
```

### Перевірка реального клієнтського запиту

Фінальна перевірка виконується на окремому клієнті, єдиний маршрут IPv4 за
замовчуванням якого веде до gateway. Скопіюйте `scripts/client-check.py` із
довіреної машини, де є робоча копія репозиторію і доступ до адреси керування
клієнта:

```sh
scp scripts/client-check.py CLIENT_USER@CLIENT_MANAGEMENT_IP:/tmp/tg-client-check.py
ssh CLIENT_USER@CLIENT_MANAGEMENT_IP
```

Адреса керування потрібна лише для відкриття термінала. Уже на клієнті перевірте
маршрут і запустіть скрипт:

```sh
ip -4 route show default
ip -4 route get 1.1.1.1
python3 /tmp/tg-client-check.py --gateway 192.168.91.1
```

Обидві команди маршрутизації мають вибрати `192.168.91.1`. Успішний результат
виглядає так:

```text
CLIENT_ROUTE PASS gateway=192.168.91.1 dev=eth1
CLIENT_DNS PASS addresses=2
CLIENT_HTTPS PASS request_id=0123456789abcdef0123456789abcdef
PUBLIC_EXIT id=0123456789ab
```

- `gateway` — наступна машина на маршруті, а `dev` — мережевий інтерфейс клієнта;
- `addresses` — кількість IPv4-адрес, які DNS повернув для публічного echo-сервісу;
- `request_id` — нова випадкова мітка, яку повернув echo-сервіс. Вона підтверджує,
  що JSON-відповідь належить саме цьому запиту;
- `PUBLIC_EXIT id` — короткий відбиток адреси джерела, яку побачив echo-сервіс.

На gateway виконайте `sudo python3 scripts/tgctl.py status` і порівняйте
`PUBLIC_EXIT id` з `active_exit_ids`. Однаковий відбиток на обох машинах означає,
що клієнтський запит вийшов через проксі з активного пулу. Відбиток дозволяє не
виводити справжню адресу під час звичайної перевірки, але не є засобом захисту.
Якщо сама адреса секретна, не публікуйте й відбиток.

Стандартний echo-сервіс `https://echo.devdays.net.ua/` зручний для першого запуску,
але його оператор бачить зовнішні адреси проксі. Для постійної перевірки розгорніть
власний [TransparentGatewayEcho](https://github.com/Va1b0rt/TransparentGatewayEcho).
Укажіть його URL під час `configure` і передайте ту саму адресу через
`client-check.py --url`.

### Перевірка відновлення після перезавантаження

Після успішного клієнтського запиту можна додатково перезавантажити хост і
переконатися, що systemd повертає gateway до роботи без ручної команди Compose:

```sh
sudo systemctl reboot
```

Після повторного підключення до gateway виконайте:

```sh
sudo systemctl status transparent-gateway.service --no-pager
cd /path/to/TransparentGateway
sudo python3 scripts/tgctl.py status
```

Коли `ACTIVE_POOL` знову стане готовим, повторіть клієнтську перевірку.

## Робоча конфігурація

Для створення робочих файлів використовуйте скрипт налаштування першого запуску. Файли
із закінченням `.example` лише описують формат: вони містять демонстраційні адреси
та паролі й не можуть бути запущені без змін. Не копіюйте їх поверх файлів,
створених командою `configure`.

Після редагування робочих файлів перевірте конфігурацію та перезапустіть службу тим
самим шляхом:

```sh
sudo python3 scripts/tgctl.py check
sudo systemctl restart transparent-gateway.service
```

Швидкий запуск підтримує один локальний конектор `jsonl_inventory`, у якому може бути
кілька дозволених проксі. HTTPS-джерела й розгортання з фіксованою версією описано в
[`deploy/README.md`](deploy/README.md). Не вмикайте їх через обхід
`tgctl.py check` і запуск неперевіреної конфігурації Compose.

Основні змінні середовища:

| Змінна | Призначення |
| --- | --- |
| `CLIENT_CIDR` | Перехоплюються лише пакети з цієї дозволеної IPv4-мережі. Значення `0.0.0.0/0` заборонено. |
| `DNS_DEFAULT_RESOLVER_IPS` | Список адрес через кому, для яких використовується DoH-маршрут. |
| `DNS_DOH_IP` | Фіксована IPv4-адреса DoH-сервера. |
| `DNS_DOH_SERVER_NAME` | Значення TLS SNI та HTTP Host для перевірки сертифіката. |
| `DNS_TCP_TIMEOUT_SECONDS` | Час очікування обміну DNS-over-TCP. |
| `DNS_MAX_CONCURRENCY` | Максимальна кількість одночасних DNS-запитів. |
| `POOL_SIZE` | Максимальна кількість перевірених проксі, які використовує gateway. |
| `RESERVE_SIZE` | Максимальна кількість кандидатів у знімку резервного пулу. |
| `MIN_SCORE_THRESHOLD` | Необов’язкова нижня межа оцінки ranker. |
| `FETCH_INTERVAL_SECONDS` | Інтервал оновлення дозволених джерел. |
| `VALIDATION_INTERVAL_SECONDS` | Інтервал перевірки протоколу й анонімності. |
| `ANONYMITY_CHECK_URL` | URL контрольованого оператором JSON echo-сервісу для прямої перевірки та перевірки через кожного кандидата. |
| `ANONYMITY_CLIENT_IPS` | Необов’язковий список додаткових прямих/NAT-адрес, які ніколи не повинні витікати. |
| `PROXY_VALIDATION_TIMEOUT_SECONDS` | Повний час очікування прямої перевірки та перевірки кожного проксі. |
| `ASN_MAX_DATABASE_AGE_SECONDS` | Максимально допустимий вік локальної перевіреної ASN MMDB. |
| `ASN_UPDATE_INTERVAL_SECONDS` | Інтервал оновлення ASN-бази з перевіркою контрольної суми. |
| `RANK_INTERVAL_SECONDS` | Інтервал публікації резервного й активного пулів. |
| `UNKNOWN_ASN_PENALTY` | Дільник оцінки для зовнішньої адреси без перевіреного ASN. |
| `MAX_UNKNOWN_ASN_RATIO` | Максимальна частка кандидатів із невідомим ASN в активному пулі. |

### Розмір пулу

`150` — приклад для одного розгортання, а не обмеження протоколу чи зашита в код
константа. `POOL_SIZE` задає максимальну кількість перевірених проксі, які gateway
може використовувати одночасно. У прикладі за замовчуванням указано `150`:

```env
POOL_SIZE=150
RESERVE_SIZE=700
MIN_SCORE_THRESHOLD=0
```

Ranker публікує не більше `RESERVE_SIZE` оцінених кандидатів і копіює перші
придатні `POOL_SIZE` записів до активного знімка. `POOL_SIZE` має бути меншим
або дорівнювати `RESERVE_SIZE`, щоб після тимчасового відкладення невдалого
проксі залишався резерв. Якщо остаточну кількість має визначати якість, укажіть
`MIN_SCORE_THRESHOLD`; тоді активний пул може містити менше записів, ніж
`POOL_SIZE`.

Вибирайте ці значення за виміряною кількістю одночасних з’єднань, можливостями
зовнішніх проксі та потрібним запасом на відмови, а не просто копіюйте `150`. Для
невеликого стенда зазвичай достатньо 8–20 проксі. Більшому дозволеному набору
може знадобитися більший резерв. Поточна реалізація оцінює кандидатів за реальною
підтримкою протоколу, анонімністю, затримкою, стабільністю та мережевими даними,
отриманими за перевіреною зовнішньою IP-адресою. Проєкт не шукає публічні проксі.

### Реєстр конекторів

Цей розділ описує розширюваний API конекторів, а не обмежений швидкий запуск з одним
конектором, який приймає `tgctl.py check`. Для HTTPS-джерела або іншого джерела під
керуванням оператора використовуйте розгортання з фіксованою версією.

Конфігурація містить лише список дозволених типів і активні екземпляри:

```json
{
  "allowed_connector_types": ["jsonl_inventory", "http_json_feed"],
  "active_connectors": [
    {
      "type": "jsonl_inventory",
      "name": "managed-socks-pool",
      "path": "/inventory/upstreams.jsonl"
    }
  ]
}
```

Щоб додати вбудований конектор, реалізуйте `collect()` як асинхронний ітератор у новому
модулі каталогу `validator/sources/`, імпортуйте клас і явно викличте
`CONNECTOR_REGISTRY.register()` у `validator/sources/__init__.py`. Потім дозвольте
його тип і додайте активний екземпляр до `inventory/connectors.json`. Fetcher та
наступні стадії змінювати не потрібно.

### Список зовнішніх проксі

Канонічний кандидат містить `host`, `port`, `protocol`, `source`, необов’язковий
`credential_ref` та необов’язкові текстові метадані. Основний модуль нормалізації
досі
приймає застаріле поле `endpoint` на вході окремих конекторів, але швидкий запуск
відхиляє його, щоб нові встановлення використовували окремі `host` і `port`. Для
сумісності з gateway у знімках зберігаються обидві форми. Мінімальний запис SOCKS5 без
авторизації:

```json
{"host":"proxy.example","port":1080,"protocol":"socks5"}
```

`protocol` може мати значення `http`, `https`, `socks4` або `socks5`. Авторизація
проксі необов’язкова. Коли validator або gateway потрібні дані доступу, список
містить лише непрозоре посилання, а обидва сервіси читають значення з файла
секретів, який Git ігнорує:

```json
{
  "provider-1": {
    "username": "example-user",
    "password": "example-password"
  }
}
```

Не додавайте `.env`, справжній список проксі або
`secrets/proxy-credentials.json` до системи контролю версій. Непривілейована група
контейнера має читати файл із даними доступу, але він не повинен бути доступним
усім користувачам. Сервіси Compose працюють із GID `65532`:

```sh
chown root:65532 secrets/proxy-credentials.json
chmod 640 secrets/proxy-credentials.json
```

## Перевірка запущеного gateway

Звичайний стан показує `tgctl.py status`. Якщо запуск завершився помилкою,
перевірте службу й останні журнали контейнерів, не виводячи знімки Redis або
розгорнуту конфігурацію Compose:

```sh
sudo systemctl status transparent-gateway.service --no-pager -l
sudo journalctl -u transparent-gateway.service --no-pager -n 100
sudo docker compose ps
sudo docker compose logs --tail 100 validator gateway
```

Знімки Redis містять адреси проксі, перевірені зовнішні адреси та посилання на
набори даних доступу. Самих паролів там немає, але цей вивід усе одно не варто
додавати до публічних звітів про помилки або скріншотів. Перевірка стану контейнера
підтверджує
лише те, що локальний relay приймає TCP-з’єднання. Повний маршрут перевіряється з
окремого клієнта.

Перед використанням проєкту на спільному хості перегляньте
`gateway/entrypoint.sh`: привілейований контейнер gateway змінює `iptables` і
маршрутизацію за правилами на хості.

## Розширена перевірка DNS

На клієнті всередині `CLIENT_CIDR` виконайте звичайний запит і запит до явно
вказаного DNS-сервера:

```sh
dig example.com +short
dig @8.8.8.8 example.com +short
```

На gateway перевірте, які гілки обробили пакети:

```sh
sudo iptables -t nat -vnL TG_DNS_DOH
sudo iptables -t mangle -vnL TG_DNS_TPROXY
```

Перший запит збільшує лічильник `TG_DNS_DOH`, а другий — лічильник правила TPROXY
у `TG_DNS_TPROXY`.

Щоб довести відсутність прямих з’єднань із DNS-серверами, захопіть трафік до
проксі та обох можливих прямих адрес на зовнішньому інтерфейсі:

```sh
sudo tcpdump -nn -ni EXTERNAL_INTERFACE \
  '(host PROXY_IP and tcp port PROXY_PORT) or \
   (host 1.1.1.1 and tcp port 443) or \
   (host 8.8.8.8 and tcp port 53)'
```

Під час двох команд `dig` захоплення має показати TCP-з’єднання з
`PROXY_IP:PROXY_PORT` і не повинно показувати прямих TCP-з’єднань із
`1.1.1.1:443` або `8.8.8.8:53`.

Корисні журнали relay для маршруту до явно вказаного сервера виглядають так:

```text
[udp2tcp-dns] tcp response ... bytes from ('8.8.8.8', 53)
[udp2tcp-dns] udp reply sent to ('CLIENT_IP', CLIENT_PORT)
```

## iptables і маршрутизація за правилами

Під час запуску створюються належні проєкту ланцюжки `TG_*`:

- клієнтський TCP спрямовується через `REDIRECT` до `redsocks` на порті `12345`;
- UDP/53 до стандартного DNS-сервера спрямовується до DoH relay на порті `5053`;
- інший трафік UDP/53 передається прозорому DNS relay на порті `5353` через
  TPROXY;
- створені локально TCP-сокети з позначкою `0x53` спрямовуються до `redsocks`;
- позначка `0x1/0xff` і таблиця маршрутів 100 доставляють TPROXY-пакети локально.

Повна маска байта має значення: `0x1/0xff` не повинна одночасно збігатися з
позначкою DNS relay `0x53`.

Під час штатної зупинки entrypoint видаляє переходи, ланцюжки, policy rule і
маршрут таблиці 100. Після примусової зупинки або відмови хоста перевірте правила
перед повторним запуском:

```sh
sudo iptables-save
sudo ip rule show
sudo ip route show table 100
```

## Тести

Запустіть модульні тести з кореня репозиторію:

```sh
python3 -m pip install -r requirements-dev.txt
python3 -m pytest tests
```

Модульні тести перевіряють нормалізацію конекторів, авторизацію через посилання на
секрети, розбір CONNECT, перевірку протоколу SOCKS5, класифікацію анонімності та
отримання початкової адреси призначення. Поведінку TPROXY в ядрі й прозорої адреси
джерела перевіряйте повними VLAN-тестами, описаними вище.

## Обмеження

- підтримується лише IPv4;
- прозоре перехоплення охоплює TCP і UDP/53, але не довільний UDP-трафік;
- QUIC/HTTP3 через UDP/443 не проксіюється, тому під час TCP-тестів його потрібно
  вимкнути;
- явно вказані DNS-сервери мають приймати DNS over TCP на порті 53;
- доступність зовнішніх проксі може змінюватися, тому для постійного використання
  потрібні моніторинг і достатньо надійний дозволений пул;
- для HTTP підтримується Basic proxy auth, для SOCKS5 — логін і пароль, для
  SOCKS4 — User ID. Digest, NTLM, Negotiate та інші схеми не реалізовані;
- перевірка анонімності залежить від коректності й доступності налаштованого
  echo-сервісу під керуванням оператора;
- можливість DNS/TCP окремо перевіряється gateway під час використання проксі.

## Безпека

- Використовуйте лише власні проксі або проксі, на які маєте явний дозвіл.
- Зберігайте дані доступу поза списком проксі та Redis.
- Не відкривайте Redis за межі локального інтерфейсу.
- Мережа керування не повинна входити до `CLIENT_CIDR`.
- Перед використанням gateway на спільному хості перегляньте правила фільтрації
  пакетів.
