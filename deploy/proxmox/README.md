# Clean Proxmox template: stage 1

This is the first implementation stage, not a complete deployment procedure.
The template is imported from an official Debian 13 cloud image and is **never
booted**. No application checkout, Redis data, `.env`, proxy inventory, credentials,
or reused guest SSH host keys are added to its disk. SSH authorization and network
identity are injected into each clone's cloud-init drive.

The image build is pinned to `20260831-2587`. The script downloads the image and
SHA-512 manifest over HTTPS from the same immutable Debian build directory,
checks the checksum and qcow2 integrity, and records the files on the Proxmox host.

Run as root on a Proxmox node with `local-lvm`, a management bridge `vmbr0`, and
capacity for a template plus a full 24 GiB clone. The bridge helper creates only
`vmbr91` and `vmbr_tglab`, both with no physical ports and no host IP addresses;
it activates only those bridges, without reloading the management network.
Review and change the example subnets before using these scripts on another site.

```sh
./prepare-lab-bridges.sh
./create-clean-template.sh
pvesm add dir tg-snippets --path /var/lib/vz/tg-snippets --content snippets --nodes pve
install -d -m 0750 /var/lib/vz/tg-snippets/snippets
SSH_PUBLIC_KEYS=/root/tg-rollout/approved-keys.pub ./clone-stage1.sh
```

The public-key file must contain the operator's approved SSH public keys. No
password or private key is passed to cloud-init. The initial admin is `tgadmin`
with passwordless sudo; SSH uses keys. `ciupgrade=0` deliberately keeps this first
stage limited to identity/network provisioning. Package installation and the
bootstrap entry point will be implemented in stage 2.

The dedicated `tg-snippets` storage holds per-clone **identity-only** user-data.
Change `--nodes pve` to your node name. Keep this storage available to the VM; it
is local to that node, so cross-node migration would require copying its snippets.
Network and instance metadata are still generated by Proxmox for each clone.

The first lab clone (211) exposed a real compatibility issue: Proxmox's generated
`user: tgadmin` scalar produced `extended_status: degraded done` and a cloud-init
deprecation warning. SSH and the three networks still worked. The renderer now
uses the documented `users` list. The corrected first-boot check uses a **new**
clone (212, `tg-repro-02`) from the same untouched template. VM 211 is stopped and
retained as evidence; do not start it while 212 uses the same addresses.
To reproduce the corrected lab attempt after stopping 211:

```sh
VMID=212 VM_NAME=tg-repro-02 SSH_PUBLIC_KEYS=/root/tg-rollout/approved-keys.pub ./clone-stage1.sh
```

Reference: [cloud-init users and groups](https://docs.cloud-init.io/en/latest/reference/modules.html#users-and-groups).

Default example resources:

| Item | Value |
| --- | --- |
| Template | 9001 / debian13-tg-clean-template |
| Clone | 211 / tg-repro-01 |
| CPU / memory / disk | 2 vCPU / 2 GiB / 24 GiB |
| net0 / eth0 / vmbr0 | 192.168.88.114/24, default via 192.168.88.1 |
| net1 / eth1 / vmbr91 | 192.168.91.1/24, isolated clients |
| net2 / eth2 / vmbr_tglab | 10.10.20.2/24, isolated proxy/echo lab |

The clone gets new MAC addresses. Proxmox generates network config **for that
clone**, with both `name: ethN` and `mac_address` for all three NICs. Do not reuse
another clone's generated network configuration: its MAC bindings would be wrong.
Deployment must later verify the expected interface/address mapping explicitly.

Inspect on Proxmox:

```sh
qm config 9001 | grep -E '^(name|template|boot|cores|memory|scsi0|ide2|net[012]):'
qm config 212 | grep -E '^(name|cores|memory|scsi0|ide2|net[012]|ipconfig[012]):'
qm cloudinit dump 212 network
```

Inspect inside the new clone:

```sh
ssh tgadmin@192.168.88.114
hostname
. /etc/os-release; printf '%s\n' "$PRETTY_NAME"
sudo cloud-init status --long
ip -br -4 address
ip -4 route
for p in /opt/transparent-gateway /etc/transparent-gateway /var/lib/docker /var/lib/redis; do
    if sudo test -e "$p"; then printf 'FAIL exists: %s\n' "$p"; else printf 'PASS absent: %s\n' "$p"; fi
done
```

Expected: Debian 13, cloud-init done with no errors, three mapped IPv4 interfaces,
one default route on eth0, four absent application/data paths. This proves the
initial host state; it does not claim application readiness.

References: [Proxmox Cloud-Init support](https://pve.proxmox.com/pve-docs/pve-admin-guide.html#qm_cloud_init),
[qm command reference](https://pve.proxmox.com/pve-docs/qm.1.html),
[pinned Debian image directory](https://cloud.debian.org/images/cloud/trixie/20260831-2587/).

## Full lab recreate and repeated reboot

`recreate-lab.py` is the operator orchestration for the article's exact lab topology.
Run it from a clean committed checkout on ARIS as root. It checks template 9001,
requires VM216 to be absent, saves only the six protected runtime files from
VM214, and sends an immutable Git bundle to Proxmox. It gracefully stops VM214
before creating VM216 (`tg-repro-05`, management `192.168.88.116`) because they
share the isolated client gateway and lab addresses. VM215 remains the client.
Existing lab VMs are preserved; VM204 is not a target of any operation.

The clone's cloud-init installs packages and runs host bootstrap. The operator
script then automatically delivers source and secrets separately over SSH,
deploys the pinned commit, installs systemd, checks client DNS/TCP/local/public
echo and secrets, reboots the clone and repeats the checks. No Redis data,
container images, guest disks or SSH host keys are copied from VM214. The new
SSH key is obtained through the authenticated Proxmox guest agent before strict
SSH login. This is operator-driven automation; cloud-init itself contains no
application secrets and does not fetch them from a public URL.

```sh
python3 deploy/proxmox/recreate-lab.py --evidence /root/tg-recreate-evidence
python3 deploy/verify-recreate.py --evidence /root/tg-recreate-evidence
```

The evidence directory is created exclusively with mode 0700 and holds a
protected runtime backup as well as logs. Do not commit or publish its contents.
The screenshot verifier prints only safe summaries and fresh readiness results.
A failed run stops, records its stage, and preserves the VM and evidence. It does
not perform repairs or silently reuse an old clone. After correcting an actual
failure, adapt the reviewed lab constants and use a new VMID and evidence path
for a new clean attempt. Do not restart VM214 while VM216 owns the shared isolated
addresses. The read-only screenshot verifier can be repeated without redeploying
or rebooting anything.

The application commit is pinned; Debian package repositories and some Docker
base image tags are not frozen snapshots. Successful recreate proves the tested
procedure and environment, not indefinite byte-for-byte reproducibility.
